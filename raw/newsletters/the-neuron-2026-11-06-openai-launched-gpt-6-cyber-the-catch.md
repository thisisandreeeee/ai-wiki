# 😼 OpenAI's GPT-6 Cyber Can Hack Better. Can It Stay Within the Rules?

OpenAI just released [GPT-6 Cyber](https://openai.com/index/introducing-gpt-6-cyber/), a version of GPT-6 Astra built to find security holes and write exploits: code that takes advantage of a specific bug. OpenAI rates it “Critical” for cybersecurity, the highest risk tier in its internal framework. _Not exactly a subtle job description._

How much stronger is it? On ExploitGym, a test of whether AI can exploit known vulnerabilities, Cyber scored **48.5%, up from 32.1%** for GPT-5.6 Cyber. That's roughly 51% better. Researchers also produced working exploits for **948 Linux kernel vulnerabilities**, [the experiment we covered yesterday](https://www.theneuron.ai/digest/everything-that-happened-in-ai-today-thursday-november-5-2026/).

But here's the question that matters more: **Can it stay inside the job it was authorized to do?** OpenAI tested that with a honeypot, an isolated environment containing one approved target and other deliberately vulnerable systems the agent was forbidden to touch. Think of a hallway full of unlocked doors where your assignment covers exactly one.

Without extra deployment safety instructions, GPT-5.6 Cyber went through a forbidden door in 5.51% of graded runs. GPT-6 Cyber did so in just **0.07%**, meaning it stayed within scope 99.93% of the time. With OpenAI's deployment instructions enabled, the tested runs showed zero violations. _Big improvement. Still a lab test, not a lifetime guarantee._

There's another catch: when told to stop, Cyber complied correctly 73% of the time, versus 78.38% for Astra. It also sometimes omitted blockers from its final reports. So stronger hacking ability doesn't automatically mean better judgment or communication. For now, access is restricted through [Daybreak Red](https://help.openai.com/en/articles/20001258-openai-daybreak-trusted-access-for-cyber-overview), with separate approval and additional security controls.

**Why it matters: **This could help defenders find bugs before criminals do. Mozilla said early access to frontier models helped Firefox ship [more than seven times as many security fixes](https://blog.mozilla.org/en/firefox/privacy-security/defending-patch-gap/) as in the comparable 2025 period. But that creates another race: once a fix is public, attackers may work backward from it while users are still waiting to install updates. That's the _patch gap_.

So the real test isn't how many locks Cyber can pick. It's whether organizations can keep it inside approved systems, turn discoveries into patches, and get those patches installed fast enough. [Our full breakdown](https://www.theneuron.ai/news/openais-gpt-6-cyber-can-hack-better-can-it-stay-within-the-rules/) has the benchmarks and sourcing.

# 🎓 AI Skill of the Day: Turn an AI mistake into a regression test for your instructions

Ever rewrite a prompt, a style guide, or a checklist until it _reads_ clearer, then discover it quietly broke something that used to work? That happens when we judge instructions by how they look instead of how an AI actually performs with them.

A new open-source tool called [Gauge](https://github.com/gauge-sh/gauge-cli) builds the fix into its workflow. It runs a coding agent (Claude Code, Codex, Pi, or OpenCode) against your product's docs or Skill, records the session, and shows you where the agent got stuck. The local version runs in Docker. Its own example: you write a Skill describing your team's release-note format, create a task (“write notes for version 1.2.0 covering a new feature and a bug fix”) plus a pass/fail check on the format, and run it. Then you edit the Skill, rerun the exact same task, and compare the two batches. Gauge calls this hillclimbing: change one thing, measure whether it helped, repeat.

You don't need Gauge to steal the idea. The rerun is the whole trick. It's a regression test, which is a check you repeat after every change to make sure you didn't break something that worked. Here's our adaptation for any prompt you reuse, like a weekly brief, a customer reply, or a research checklist:

1. Pick one representative task and write down what a good result must contain.

2. When the AI misses, save that failure as your test and change only the instruction that caused it.

3. Rerun the original task and compare the new output against the same criteria.

Copy/paste this after a weak result (our prompt, not Gauge's):

```
Review the result against these acceptance criteria: [criteria]. Identify the earliest instruction that was missing, ambiguous, or ignored. Propose one minimal instruction change, then show how that change would alter the failed part without rewriting unrelated rules.
```
_Keep whichever version passes. The rewrite that felt nicer but scored worse goes in the bin._
